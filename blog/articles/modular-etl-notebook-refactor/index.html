Breaking Apart a Monolithic ETL Codebase: Why We Moved from File-Per-Layer to Folder-Per-Entity

Oselio Candido · Sep 2, 2026 · 8 min read

I previously wrote about restructuring a FastAPI backend as a modular monolith: instead of organizing the codebase around technical layers, each business module owns its domain, application logic, infrastructure, and presentation.

The same principle applies surprisingly well to ETL code.

A Databricks pipeline naturally encourages organization by pipeline layer: 

raw/
stage/
bus/
serve/

That makes sense at first. But as the number of tables grows, another question becomes more important:

What is the unit of change?

In this pipeline, it was almost always a business entity or table.

Yet the codebase was organized around technical layers.

The result was predictable: a small number of files gradually became monoliths.

The Problem

A warehouse-operations reporting pipeline had grown table by table into a structure where code was grouped by pipeline layer rather than by the business object it belonged to.

By the time the pipeline needed a serious refactor, two files had effectively become small monoliths:

File Lines Contents
tables_bus.py 639 Definitions for every bus-layer table
02_stage_to_bus.py 394 Transformations for those same tables

There were eleven fact and dimension tables in the bus layer.

The schema for fact_order_fulfillment lived somewhere inside one file. Its transformation logic lived somewhere else inside another.

The connection between them was mostly a naming convention. 

tables_bus.py
├── DimWarehouseDetails
├── FactOrderFulfillment
├── FactInventoryMovement
├── ...
└── 8 more tables

02_stage_to_bus.py
├── build_dim_warehouse_details()
├── build_fact_order_fulfillment()
├── build_fact_inventory_movement()
├── ...
└── 8 more transformations

Changing one table meant navigating two unrelated regions of the repository.

A simple change

Suppose I needed to add a column to fact_order_fulfillment.

That meant:

  1. Open a 639-line file.
  2. Find the table definition among ten other tables.
  3. Modify the schema.
  4. Open a different 394-line file.
  5. Find the transformation for the same table.
  6. Modify the transformation.

Neither file was conceptually about fact_order_fulfillment.

Both were containers for everything in the bus layer.

That distinction becomes important as the pipeline grows.

When Grouping by Layer Stops Scaling

Grouping by technical layer is not inherently wrong.

It mirrors how medallion architectures are normally described: 

Raw → Stage → Bus → Serve

And when the pipeline had only three tables, a file such as this was perfectly reasonable: 

tables_bus.py

One file was easier than creating several directories for a handful of tables.

The problem appeared when table count grew.

The structure of the codebase stayed fixed: 

one file per layer

while the amount of code inside that file grew with every new table.

Those are two independent concerns: 

Pipeline complexity → grows with table count
Code organization   → stays fixed around pipeline layers

Eventually, unrelated entities accumulate inside the same files simply because they happen to belong to the same technical layer.

The result looks like this: 

# tables_bus.py

class DimWarehouseDetails(BaseTable):
    __tablename__ = "dim_warehouse_details"

    warehouse_sk = Column(BigInteger, primary_key=True)
    warehouse_id = Column(String)
    region = Column(String)
    # ... 42 more columns


class FactOrderFulfillment(BaseTable):
    __tablename__ = "fact_order_fulfillment"

    order_fulfillment_sk = Column(BigInteger, primary_key=True)
    warehouse_sk = Column(
        BigInteger,
        ForeignKey("dim_warehouse_details.warehouse_sk")
    )
    # ... 18 more columns


class FactInventoryMovement(BaseTable):
    __tablename__ = "fact_inventory_movement"

    # another unrelated table

These tables may have dependencies at the data level.

That does not mean their implementation code needs to live together.

The Practical Cost

The cost was not theoretical architecture purity. It showed up during ordinary development.

Two-file navigation

A change to one table often required edits in multiple large files.

The relevant code was connected by convention: 

FactOrderFulfillment
        ↓
find the matching function somewhere else
        ↓
build_fact_order_fulfillment()

The developer had to reconstruct that relationship every time.

Merge conflicts between unrelated work

Two engineers could modify completely unrelated tables and still collide because both changes happened inside: 

tables_bus.py

The conflict itself was often easy to resolve.

The annoying part was the review.

After resolving it, you had to verify that unrelated definitions had not been accidentally reordered, duplicated, or modified.

The repository structure created coupling that did not exist in the business logic.

File size became a proxy for table count

The more tables we added, the larger the shared files became.

There was no natural boundary.

The organizing rule was effectively:

Keep putting tables here because they belong to the bus layer.

That works until "the bus layer" becomes a category containing dozens of unrelated implementation units.

The Alternatives

We considered several ways to split the code.

1. Keep grouping by layer, but split the files

The smallest change would have been something like: 

bus/
├── fact_tables.py
├── dimension_tables.py
└── transformations.py

This improves file size.

But it does not change the underlying relationship.

A table's schema and transformation logic still live in different places.

You still navigate by asking:

Which shared file contains the part I need?

rather than:

Where does this entity live?

2. One file per table, centralized transformations

Another option was: 

bus/
├── data/
│   ├── dim_warehouse_details.py
│   ├── fact_order_fulfillment.py
│   └── fact_inventory_movement.py
│
└── transformations.py

Finding schemas becomes trivial.

But the transformation file still grows indefinitely.

And that is often where the most interesting logic lives:

  • joins
  • validation
  • normalization
  • surrogate key generation
  • business rules
  • data quality decisions

We would have solved only half of the problem.

3. Folder per entity

The option we chose was to make the entity the primary organizational boundary.

Each table gets its own module containing the code that belongs to that table. 

warehouse_ops_report/
├── 02_stage_to_bus.py
│
└── bus/
    ├── dim_warehouse_details/
    │   ├── data.py
    │   └── transformations.py
    │
    ├── fact_order_fulfillment/
    │   ├── data.py
    │   └── transformations.py
    │
    └── fact_inventory_movement/
        ├── data.py
        └── transformations.py

Now the question:

Where is the code for fact_order_fulfillment?

has an obvious answer: 

bus/fact_order_fulfillment/

The schema and transformation logic are colocated because they usually change together.

This was the key architectural decision.

The Layer Became Orchestration

Once the entity owned its own implementation, the layer-level script no longer needed to contain the business logic.

It only needed to orchestrate execution.

Before, 02_stage_to_bus.py contained hundreds of lines of transformations.

After the refactor, it became intentionally boring: 

from bus.dim_warehouse_details.transformations import (
    build_dim_warehouse_details,
)

from bus.fact_order_fulfillment.transformations import (
    build_fact_order_fulfillment,
)

from bus.fact_inventory_movement.transformations import (
    build_fact_inventory_movement,
)


def run(spark, cfg):
    build_dim_warehouse_details(spark, cfg)

    build_fact_order_fulfillment(spark, cfg)

    build_fact_inventory_movement(spark, cfg)

The orchestration layer now answers a single question:

What runs, and in what order?

The entity modules answer a different question:

How is this table built?

That separation turned out to be more valuable than simply reducing file size.

A Change Now Has a Physical Boundary

Consider the same change as before:

Add a column to fact_order_fulfillment.

Previously: 

tables_bus.py
        +
02_stage_to_bus.py

Both were shared files containing unrelated entities.

After the refactor: 

bus/
└── fact_order_fulfillment/
    ├── data.py
    └── transformations.py

The change starts with the entity.

The repository structure reflects the unit of work.

This also reduces accidental coupling during development.

Two engineers modifying: 

fact_order_fulfillment/

and: 

fact_inventory_movement/

are much less likely to touch the same files.

The codebase boundary now matches the change boundary.

The Unexpected Result: More Files, Less Code

At first, the refactor looked like it would create a lot of scaffolding.

We were splitting eleven tables and their transformations into a much larger number of smaller modules.

That usually sounds like:

More folders + more files = more boilerplate.

The opposite happened.

The refactor removed more lines than it added.

Why?

Because the large shared files hid a surprising amount of repeated code.

Once each table lived in a focused module, the repeated patterns became much easier to see.

That led to a second refactoring pass.

What Splitting Made Visible

Folder-per-entity solved the navigation and merge-conflict problems.

But it exposed another problem.

Several staging transformations contained almost identical logic.

Across nine different source feeds, variations of the same operations appeared repeatedly:

  • normalize an identifier
  • trim whitespace
  • uppercase values
  • remove invalid null records
  • normalize headers
  • parse dates

Before the refactor, those patterns were buried inside large files.

For example: 

# stg/warehouse/transformations.py

df = df.withColumn(
    "warehouse_id",
    trim(upper(col("warehouse_id")))
)

df = df.filter(
    col("warehouse_id").isNotNull()
)

Another transformation implemented essentially the same rule: 

# stg/task_header/transformations.py

df = df.withColumn(
    "task_id",
    upper(trim(col("task_id")))
)

df = df.na.drop(
    subset=["task_id"]
)

The implementations were not identical.

That was exactly the problem.

They had drifted.

Extracting the Shared Rule

Once the duplication was visible, the common behavior could be expressed explicitly. 

# tools/dataframe_utils/dataframe_normalizers.py

def normalize_identifier_column(
    df: DataFrame,
    column: str,
) -> DataFrame:
    """Normalize an identifier and remove null values."""

    return (
        df
        .withColumn(
            column,
            trim(upper(col(column))),
        )
        .filter(
            col(column).isNotNull()
        )
    )

The nine transformations that previously implemented their own version of this rule could now call the same function.

That had two benefits.

First, the business transformations became smaller.

Second, the shared behavior became independently testable.

The utility has no dependency on:

  • a specific table
  • orchestration
  • a Spark job
  • a configuration object

It accepts a DataFrame and returns a DataFrame.

That makes it practical to test directly.

Splitting the monolith did more than make each piece easier to find. It made the duplication between pieces visible.

A 639-line file can hide repetition inside its own bulk. Eleven focused modules make repeated patterns much harder to ignore.

The Architectural Lesson

The important change was not simply:

One folder per table.

The broader principle is:

Organize code around the things that change together.

In this pipeline, a table's:

  • schema
  • transformation rules
  • validation
  • data-quality decisions

are usually part of the same unit of change.

The fact that every table happens to pass through the bus layer is less useful as an organizational boundary.

The pipeline layer still matters.

It defines the data flow: 

Raw → Stage → Bus → Serve

But it no longer needs to be the primary unit of implementation.

The layer defines where the data is in the pipeline.

The entity defines where the code belongs.

Those are different responsibilities.

The Outcome

Neither refactor changed what the pipeline computes.

The output remained the same.

What changed was the shape of the codebase.

  • 121 files touched, with net lines removed. Much of the original size was repeated boilerplate rather than unique transformation logic.
  • A follow-up utilities pass added shared abstractions and tests. A meaningful portion of the new code was test coverage for logic that had previously existed only as duplicated inline implementation.
  • A schema change to one table now starts in one module, instead of requiring navigation through multiple shared files containing unrelated tables.
  • Normalization and parsing bugs can now be fixed once, in a tested shared utility, instead of being corrected independently across several transformations.
  • The orchestration layer is now explicit about dependencies. It describes what runs and in what order instead of also containing the implementation of every transformation.

The codebase now has more files than before.

That is intentional.

A repository with fewer files is not necessarily simpler if each file contains several unrelated responsibilities.

For this pipeline, the useful measure of complexity was not:

How many files are there?

It was:

How much unrelated code do I need to understand before I can safely change this table?

Before the refactor, the answer was often hundreds of lines.

After it, the answer is usually: 

bus/
└── fact_order_fulfillment/

And that is the real reason folder-per-entity worked.

The goal was never to maximize the number of modules.

It was to make the structure of the repository reflect the structure of change.
